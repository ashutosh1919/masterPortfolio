# Security and upstream review

- **Review date:** 2026-11-12
- **Fork baseline:** `f75ebdfe9c79ee3e78defdc0c0f1921ab8dd62af` on `arena/56c04027-masterportfolio`
- **Original repository:** [ashutosh1919/masterPortfolio](https://github.com/ashutosh1919/masterPortfolio), `master` at `33b04a568a92a44e538a1795d8eab742dac47d81` when reviewed.

This is a source, dependency, configuration, and upstream issue/PR review, not a penetration test or a guarantee that the application is secure. The app is principally a static React site. The GitHub fetcher is a local build-time script; the routed site does not contain a general-purpose server, login system, or PDF upload endpoint. Findings below distinguish a vulnerable package or unsafe practice from a demonstrated remotely exploitable application vulnerability.

## Executive summary

- **The dependency stack still needs significant work.** After repairing the lockfile, `npm audit` reported **191 affected package entries: 10 critical, 47 high, 130 moderate, and 4 low**. These are npm's package-level classifications, not 191 independently demonstrated application exploits. See the exposure analysis below.
- The shipped PDF viewer uses vulnerable `react-pdf`/PDF.js versions. A documented `isEvalSupported: false` mitigation was added, but the dependencies still require a compatible upgrade.
- The old instructions asked users to grant a GitHub token every permission, and Docker previously copied local `.env` files into image layers. The guide, ignore rules, and fetcher were hardened; previously exposed tokens, images, history, and generated data still need separate review.
- The fork's baseline is exactly the head of upstream [PR #404](https://github.com/ashutosh1919/masterPortfolio/pull/404). That PR changed the dependency manifest without updating the lockfile; the original `npm ci` failed. The lockfile is now synchronized and a clean install, tests, and production build have been verified with the limitations below.
- No evidence of a compromised site or leaked credential was established. A limited pattern scan of the available tracked text found no matching GitHub token, AWS access key, or private-key header; it was **not** a full secrets or history audit.

## Changes made during this review

1. Synchronized `package-lock.json` with `package.json`. This installs the already-declared `gh-pages@5.0.0` and `react-scripts@3.4.4` instead of the old locked 2.2.0 and 3.2.0. It is not a complete dependency remediation.
2. Added `.dockerignore` exclusions for Git metadata, dependencies, build output, environment files, and `.npmrc`; expanded `.gitignore` to cover `.env.*`; replaced the README's all-permissions token advice with least-privilege guidance and an explicit warning about public `REACT_APP_` variables and old artifacts.
3. Updated `git_data_fetcher.mjs` to use GraphQL variables, require its configuration, report HTTP/GraphQL/network/write failures without logging tokens, and exit nonzero on failure. Newly fetched PRs, issues, and pinned projects are retained only when their repository is explicitly public; contributed organizations are queried from public repositories only. Existing files/history are not retroactively cleaned.
4. Changed the PR and issue queries to request the **first** 100 in descending creation order. Previously `last: 100` with descending order selected the oldest 100 when more existed. Visibility filtering happens after this limit, so fewer than 100 public results may remain; counts describe only the fetched, public subset.
5. Disabled PDF.js evaluation for the résumé viewer as the advisory's temporary workaround, and changed the active project/publication cards to focusable links with `noopener noreferrer`.
6. Made SEO structured-data rendering tolerate missing email, work experience, and certifications; added an explicit `cd masterPortfolio` onboarding step. Added stable React keys to the project, publication, pull-request, and issue lists. These are partial fixes, not blanket fixes for every empty-data case or React warning.
7. Moved Node CI to Node 22, enabled feature-branch push checks, made tests run deterministically in one process, restricted workflow tokens to `contents: read`, disabled persisted checkout credentials and install-time lifecycle scripts, and pinned actions to full SHAs verified against their tags. Datadog now skips explicitly when both secrets are unavailable, fails on partial configuration, and runs the updated Node 24 action when configured. The action code was not independently audited; Docker still needs review.
8. Replaced the hidden mobile-menu checkbox with a keyboard-operable button, a labelled navigation landmark, expanded-state feedback, Escape/focus behavior, and a visible focus indicator. Fixed the experience-card minimum-width overflow reproduced at a 320 CSS-pixel viewport. Added accessible names to social links and the footer emoji, and a footer landmark.
9. Added regression tests for the fetcher's error/privacy/ordering paths, PDF options, project links, empty SEO data, navigation and other accessibility improvements, Datadog credential handling, and eight route smoke checks with rendering dependencies mocked.
10. Corrected the separate pull-request data workflow's GraphQL syntax and output reference, updated and pinned its action, and stopped interpolating query results directly into shell code. Its existing literal `all` branch trigger remains unchanged.

## Security findings

### S1 — Outdated dependencies and development server — **High; open**

**Evidence:** `package.json:14-33`, `package-lock.json`, `Dockerfile:1-16`, `.github/workflows/nodejs.yml:19-31`.

The synchronized lock contains `react-scripts@3.4.4`, `webpack-dev-server@3.11.0`, `react-pdf@5.7.1`, and `pdfjs-dist@2.12.313`. Relevant examples:

- [GHSA-wgrm-67xf-hhpq](https://github.com/advisories/GHSA-wgrm-67xf-hhpq) and [GHSA-87hq-q4gp-9wr4](https://github.com/advisories/GHSA-87hq-q4gp-9wr4): a malicious PDF can execute JavaScript in the hosting origin when PDF.js evaluation is enabled. The current route imports a repository-owned PDF (`src/pages/resume/Resume.js:6`) and does not accept a visitor's PDF, so exploitation requires the PDF to be replaced or another untrusted-PDF path to be added. **Mitigation applied:** the `Document` receives a stable options object with `isEvalSupported: false`. This is a workaround, not a patched dependency.
- [GHSA-4v9v-hfq4-rm2v](https://github.com/advisories/GHSA-4v9v-hfq4-rm2v) describes a development-server source-exposure scenario involving a malicious page and predictable development-server URLs/configuration. Its prerequisites were not demonstrated against this exact webpack configuration. It concerns a developer's running server, not the static production build. Do not publish the development server or assume binding to localhost alone eliminates every cross-origin scenario.
- Not every critical audit entry reaches the production browser. For example, `form-data` is reached through `request` → `jsdom` → Jest in the test/build graph. The [react-dev-utils command-injection advisory](https://github.com/advisories/GHSA-5q6m-3h65-w53x) explicitly says the usual `react-scripts` use is not affected; its presence in `npm audit` alone is not evidence of command execution here.
- The baseline lock had `gh-pages@2.2.0`, affected by [GHSA-8mmm-9v2q-x3f9](https://github.com/advisories/GHSA-8mmm-9v2q-x3f9), despite the manifest declaring `^5.0.0`. Synchronizing the lock now installs 5.0.0. This removed that direct advisory from the new audit; other advisories remain.

**Recommended remediation:** upgrade `react-pdf` and PDF.js together, including the worker and the direct `pdfjs-dist` dependency, then test normal and malicious-PDF regression cases. As a migration candidate—not a tested drop-in—`react-pdf@9.0.0` declares `pdfjs-dist@4.3.136` and a React 16.8+ peer range, but its worker/module requirements must be tested with this older webpack stack. Plan a supported build-tool migration and upgrade/remove obsolete packages rather than blindly running `npm audit fix --force`. Review each advisory's reachable execution path and repeat `npm audit` after each change.

Node 20 in the Docker base reached end of life on 2026-04-30 according to the [Node.js release schedule](https://github.com/nodejs/Release/blob/main/schedule.json). The Node CI job was moved to Node 22, which was used for this review; migrate and test the Docker image as well. Node 24 has a longer support window. The `--openssl-legacy-provider` build flag is another sign that the old toolchain needs replacement; it is not, by itself, proof that production HTTPS is insecure.

### S2 — Token permissions and local credential exposure — **High if a broad token/image is exposed; safeguards added**

**Evidence:** `README.md` GitHub setup, `.gitignore`, `.dockerignore`, `Dockerfile:7-11`, `docker-compose.yaml:10-14`.

Before this review, the README instructed users to grant all token permissions. `.env.production` and similar files were not covered by `.gitignore`; with no `.dockerignore`, Docker's `COPY . ./` could bake `.env` and project `.npmrc` files into image layers. An image recipient could then extract them. This is a conditional exposure; no actual token leak was established.

The new exclusions protect **future build contexts**, not already built/pushed images, tracked files, Git history, or the Compose bind mount (`.:/app`), which still makes local files available inside the running container. Revoke and replace any exposed or unnecessarily broad token; review existing images and Git history separately. Use an expiring fine-grained token with minimal read-only access, and never put a secret in a `REACT_APP_` variable: Create React App embeds such values into the browser bundle. GitHub's token guidance confirms that fine-grained tokens include public-repository read access and recommends minimum permissions [1](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

### S3 — Private GitHub metadata in generated public JSON — **High if a privileged token is used; mitigated for new fetches**

**Evidence:** `git_data_fetcher.mjs:17-135,204-253,295-320`; generated files under `src/shared/opensource/` are imported into the site.

A token with private/internal repository access can cause GitHub to return information that should not be published. The fetcher now checks `isPrivate === false` for PR base repositories, issue repositories, and pinned repositories, rejects missing/unknown visibility, and requests `repositoriesContributedTo(privacy: PUBLIC)` for organizations. GitHub's schema describes `isPrivate` as true for private **or internal** repositories. Tests cover private and unknown entries.

This does not clean older JSON or Git history. The four requests still write independently: if one fails, successful requests may already have updated their files, failed outputs may remain stale, and a failed write can leave an incomplete file. Inspect all generated data before publication. Fetch and validate all datasets before publication, then design a transaction/recovery strategy with staged files and interruption handling; separate renames alone do not make a four-file update atomic. Add privacy-aware pagination.

### S4 — Third-party scripts, tracking, and deployment headers — **Medium; open**

**Evidence:** `public/index.html:38-69`, `src/pages/resume/Resume.js:12`, plus the locally vendored Font Awesome assets.

The default page loads Google advertising/tag scripts with the original owner's identifiers, Iconify, anime.js, CanvasJS, and remote CSS. Fixed CDN resources do not specify subresource integrity; third-party script compromise or unintended tracking affects visitors. The identifiers are configuration, not secrets. Review which libraries are actually needed, self-host or integrity-pin fixed resources where feasible, and make analytics/ads explicit opt-in with appropriate consent and privacy documentation.

No CSP or other response-header configuration is present in this repository. Hosting infrastructure may set headers independently; the live site's headers were not inspected. On a host that supports them, roll out a tested CSP in report-only mode first, then enforce a policy covering the actual scripts, Iconify requests, styles, images, and PDF worker. Also evaluate `frame-ancestors`, `X-Content-Type-Options`, HSTS for HTTPS, `Referrer-Policy`, and `Permissions-Policy`. Do not apply a generic restrictive CSP without testing: upstream [issue #276](https://github.com/ashutosh1919/masterPortfolio/issues/276) reports broken icons/avatars under CSP, and GitHub Pages does not generally allow arbitrary custom response headers.

### S5 — CI supply-chain and container hardening — **Medium; open**

**Evidence:** `.github/workflows/nodejs.yml:19-31`, `.github/workflows/pullRequestsDataFetcher.yml:9-50`, `.github/workflows/datadog-synthetics.yml:22-35`, `Dockerfile`, `docker-compose.yaml`.

The workflows now cap `GITHUB_TOKEN` permissions at `contents: read` and use full-SHA action pins. Both checkout steps disable persisted credentials, and Node CI installs with `npm ci --ignore-scripts`. Datadog explicitly skips when neither secret is available, fails if exactly one is present, and runs the pinned Node 24 action with failures enabled when both are available. The Datadog workflow is disabled in the fork's GitHub settings as observed during this review; a real Datadog run was not verified. Forked PR secrets are normally withheld—neither a write-enabled token nor an exfiltration was demonstrated. Docker's `npm install` can still execute dependency lifecycle scripts.

Keep action pins and permissions reviewed, keep secrets out of untrusted PR jobs, and review installation scripts used outside Node CI. The Docker image currently runs a development server as root and Compose publishes port 3000 as host port 3001; it is not a hardened production deployment. Use a supported, tested build image and a non-root static serving stage with appropriate hosting headers for production. `EXPOSE 3001` does not match the app's default container port 3000.

The separate `pullRequestsDataFetcher.yml` had invalid GraphQL syntax, a wrong output reference, a hardcoded owner, and direct interpolation of query output into a shell command. These were corrected and its action was updated and pinned. Its `branches: [all]` trigger still matches only a literal branch named `all`, not every branch; decide whether that trigger is intended before changing it. The query expects the repository owner to be a GitHub user, not an organization.

### S6 — External links and latent token-bearing code — **Medium/low; partially addressed**

**Evidence:** active `src/components/githubRepoCard/` and `src/components/publicationsCard/`; legacy `src/containers/projects/Projects.js`, `src/components/achievementCard/`, `src/containers/StartupProjects/`, `src/components/blogCard/`, `src/components/talkCard/`.

The active project and publication cards used `window.open` without explicitly isolating `window.opener`, and called `.focus()` even if a popup was blocked. They now use keyboard-focusable anchors with `rel="noopener noreferrer"`. Other legacy components still contain similar window-opening or named-target patterns and should be hardened before reuse.

The old `src/containers/projects/Projects.js` decodes a Base64 GitHub token in browser code. It is **not** the component imported by the current router and was not found in the inspected production source maps; this is a latent reactivation hazard, not proof that a live token is exposed. Remove or redesign it instead of storing tokens in client code. Validate URL schemes if configuration or card data ever becomes untrusted.

The loader's `dangerouslySetInnerHTML` is an HTML sink, but its current value is a static CSS template with no interpolation (`src/components/Loader/LoaderLogo.js:164`). No attacker-controlled input reaches that sink in the inspected code, so it was not classified as an exploitable XSS. Keep untrusted values out of it or move the CSS to a stylesheet.

### S7 — Public source maps and limited secret scan — **Informational**

The production build emits JavaScript source maps, which expose bundled source to site visitors. That is not a vulnerability by itself for a public portfolio, but it reinforces that client code and `REACT_APP_` values must never contain secrets. Disable public source maps only if the deployment's debugging policy calls for it; doing so does not make bundled secrets safe.

A pattern-only scan covered 1,790 tracked text files and skipped 83 binary, large, or unreadable files. It found no matches for selected GitHub-token, AWS-access-key, or private-key-header patterns. The checkout is shallow and has only one available commit, so this does not cover full history, binary content, untracked files, all secret formats, or external images.

## Prioritized improvement roadmap

1. **Immediate:** rotate any exposed/overprivileged token; inspect existing images, Git history, and generated data; restrict development-server exposure; migrate and test Docker off Node 20; inventory the 191 dependency findings by reachability.
2. **Security maintenance:** upgrade the PDF viewer and worker as a pair; migrate the deprecated build stack; remove unused dependencies/legacy token code; review action pins and workflow permissions over time; add automated dependency and secret scanning. Keep the temporary PDF workaround until the upgrade is verified.
3. **Reliability and deployment:** implement privacy-preserving cursor pagination and atomic data refresh; validate configuration before build; add route, deep-link, subpath, empty-data, and multi-page PDF tests. Test root and project-page deployments independently.
4. **Accessibility and usability:** fix the remaining contrast and page-landmark/heading issues identified below; extend automated browser coverage for navigation and experience cards; test screen readers, focus after route changes, reduced motion, zoom, and other browsers. The résumé viewer hides its text and annotation layers in `Resume.css`; provide a semantic, screen-reader-accessible résumé alternative and verify the download separately.
5. **Product features:** add optional sections and schema-validated profile settings, manually curated project details alongside GitHub projects, and optional localization. Make analytics explicitly opt-in. Replace original-owner metadata, CNAME, sitemap, and tracking IDs during customization.
6. **Performance and SEO:** evaluate removal of unused global scripts, bundle the PDF worker locally, split routes where beneficial, and generate canonical/Open Graph/sitemap values from configuration. Current static HTML includes original-owner metadata and root-relative assets.

## Verification and limitations

- `npm ci --ignore-scripts` succeeded with npm 10.9.8 and, with audit/funding output disabled in a separate scratch copy, npm 10.2.4. Both ran under Node 22.22.3; lifecycle scripts and the Docker image's Node 20 runtime were not exercised. All three workflows passed actionlint, and the pinned action tags and configured Datadog input names were checked. GitHub-hosted PR execution and a real Datadog run require separate verification.
- All 2,135 resolved lockfile entries point to `registry.npmjs.org` and include integrity hashes; this does not establish that the packages are safe. On both clean Linux installs, `npm ls --all --json` reported the optional helpers `bindings`, `file-uri-to-path`, and `nan` as extraneous despite exiting successfully; review that optional-dependency cleanup during modernization.
- `CI=true npm test -- --watchAll=false --runInBand`: **9 suites, 32 tests passed**. Eight route smoke checks used jsdom and mocked animation, charts, and PDF rendering. Datadog credential checks used test-only values, not real service calls. Existing list-key, SVG-property, Styletron, and deprecated lifecycle warnings remain. Fetcher network responses were mocked, including HTTP, GraphQL, missing user, invalid JSON, network, partial success, write error, public/private filtering, and ordering.
- `CI=true npm run build`: passed after the lockfile repair. With evaluation disabled, the bundled one-page résumé was parsed locally and rendered in headless Chromium; resizing from desktop to mobile did not reload the PDF. The browser test supplied the matching installed PDF worker in place of the CDN response. It was not a malicious-PDF exploit test or a test of the live CDN.
- All four fetcher GraphQL query shapes and the corrected workflow query were accepted by GitHub through `gh api graphql` using public accounts and reduced page sizes. A real end-to-end fetcher run with a valid PAT was not performed: Node's direct request in this sandbox failed TLS certificate verification. TLS verification was not disabled.
- A local production build was exercised in headless Chromium 153 with third-party requests blocked. Header checks covered pointer and keyboard activation, focus restoration, and layout at 320, 375, 768, 1024, 1104, and 1280 CSS pixels. The experience checks expanded each default section at 320, 375, 414, and 768 CSS pixels and tested long unbroken card text. Scoped axe-core 4.11.1 checks reported no header violations at 320 (open/closed) or 1280 pixels. Document scans of home and experience at 375 pixels and projects at 1280 pixels still flagged contrast and missing main/region landmarks; experience also had heading-order findings. For example, the default blue theme's mobile greeting text has approximately 3.1:1 contrast against its background, below the 4.5:1 threshold for normal text. These were ad hoc checks, not a comprehensive browser, visual, or accessibility audit.
- No Docker/Podman engine or assistive technology was available. Image layers, real screen-reader behavior, actual security headers/CSP, third-party scripts, live deployment, and production deep-link handling were not tested. The local static server used the app's redirect shim to reach routes. Do not interpret the report as certification of those surfaces.
- `npm audit --json` was run on 2026-11-12. The **original, internally inconsistent** lockfile reported 212 package entries (12 critical, 59 high, 133 moderate, 8 low); the synchronized lock reported 191. The first graph could not be installed with `npm ci`, and audit counts change over time. Reproduce with `npm audit --json` rather than treating these counts as permanent.
